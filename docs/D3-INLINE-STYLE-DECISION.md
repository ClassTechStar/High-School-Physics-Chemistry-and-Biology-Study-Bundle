> 结论先行的建议：**L1 动态 449 处建议按模块推进改造；L2 静态 3172 处不建议在本轮强行清零。**

## 1. 口径纠正：此前的数字是错的

本轮实测（42 个 js 文件，正则 `\sstyle\s*=\s*["'\`]` 精确匹配 HTML 属性形态）：

| 分类 | 处数 | 说明 |
|---|---|---|
| **运行时生成（动态）** | **449** | `${}` 模板插值 17 + **字符串拼接 432** |
| 真静态（纯字面量） | 3172 | 去重后仅 **1922 个唯一组合** |
| 合计 | **3621** | — |

**两处必须纠正的旧口径错误：**

1. **「20 处动态」严重低估** —— 真正的动态主体是**字符串拼接型**（`style="color:'+gradeColor+'"`），共 432 处。此前只统计了 `${}` 插值（17–20 处），漏掉了 24 倍的工作量。
2. **「3952 处 JS 样式写入」混计** —— 其中 328 处是 `el.style.prop=` / `el.style.cssText=`，属 **CSSOM 写入，`style-src 'unsafe-inline'` 根本管不到**。另有 305 处是 `ctx.fillStyle` / `ctx.strokeStyle`（**Canvas API**，与样式无关），曾被无前导空白的正则误计（「3929」之误来源）。

**不受 `style-src 'unsafe-inline'` 管辖的 328 处已从工作量中剔除**（其中 cssText 整体写 43 处已包含在内，旧输出并列显示为重复计数）。

## 3. 一次性自动化改造：已实证否决

**尝试路径**：把 js/ 侧 3623 处模板 `style="..."` 统一改名为 `data-style="..."`，
新建 `js/cssom-style-bridge.js`（MutationObserver 全局监听 + `el.style.setProperty`），
插入 DOM 后统一写入 CSSOM —— 使运行时不再产生 style 属性，从而移除 `style-src 'unsafe-inline'`。

**结果：桥接本身 100% 成功**（抽样 1147 个带 `data-style` 的元素，1147 个均生成了
对应 style 属性，零失败），**但 computed-style 回归失败**：

```
[compare] ❌ 共 2246 处差异
    dark-platform: 244   dark-chinese: 243   dark-physics: 242
    dark-chemistry: 242  dark-biology: 242   dark-english: 242
    dark-math: 241       dark-home: 239       dark-exam: 239
    light-*: 6–11（每科）
```

### 失败机制（已取证）

`theme-dark.css` 第 6 节用**字面文本属性选择器 + `!important`** 来压制内联样式
（这是「内联样式无法被普通选择器覆盖」的既有应对手法，共 **257 条选择器行**）。

桥接改为 CSSOM 写入后，浏览器把值**重新序列化**：

```html
<span data-style="background:#fee2e2;color:#b91c1c;padding:6px 12px;..."
      style="background: rgb(254, 226, 226); color: rgb(185, 28, 28); padding: 6px 12px; ...">
```

即 `#fee2e2` → `rgb(254, 226, 226)`，导致 `[style*="background:#fee2e2"]` **失配**，
暗色覆盖整体失效，暗态元素回落为浅色值（如 `color` 由 `rgb(96,165,250)` 变为 `rgb(59,130,246)`）。

### 由此得到的结论

**「属性重命名 + CSSOM 桥接」与第 6 节的文本匹配覆盖机制存在根本性冲突。**
静态内联样式要真正收敛，只剩两条路：

1. **类化 + 令牌**（D2 已验证可行）—— 但需按声明组合逐个设计，工作量随组合数线性增长；
2. **改造第 6 节选择器** —— 依赖浏览器序列化格式，脆弱且不可移植，不推荐。

**当前状态：该自动化路径已回滚，改造未落地。**
工作区已确认回到已提交的绿色基线，`npm run verify` 九阶段全绿，
computed-style 回归 18/18 组合零差异。

## 4. 修订后的路线建议

| 方案 | 范围 | 工作量 | CSP 可收紧 | 风险 | 建议 |
|---|---|---|---|---|---|
| **A-1** | 仅 L1 动态 449 处（按模块分批） | 中 | 否（静态 3172 处仍在生成 style 属性） | 低（已验证可行） | ★ 推荐 |
| **A-2** | L1 + L2 高频档（≥5 次，100 组合 / 873 处） | 高 | 否 | 中 | 可选 |
| **B** | 全量 3621 处类化 | 极高 | 是 | 极高 | 不建议本轮 |
| **0** | 维持现状，登记为已知技术债 | 0 | 否 | 无 | 备选 |

**推荐 A-1 的理由：**

- **收益真实**：消除 449 处「运行时值拼接进 style 属性」的模式，这是 D 类里唯一与安全相关的部分；
- **风险可控**：动态值多为尺寸（width/height %）与运行时计算色，theme 覆盖模式不依赖其字面文本，D 类回归已验证；
- **不虚耗**：L2 长尾 1490 处（占静态 47%）每处仅用一次，为它们造类的边际收益接近 0。

**关于 CSP 收紧的诚实结论：**
只要 js/ 侧仍有任一处生成 `style="..."` 属性字符串，`style-src 'unsafe-inline'` 就必须保留。
换言之，**D3 只有全量清零才对 CSP 有实质收益**；做一半只能换来代码规范性，不能换来安全边界收紧。
考虑到本应用离线运行、无用户生成内容，CSS 注入的实际风险极低——这也是不建议走方案 B 的核心原因。
